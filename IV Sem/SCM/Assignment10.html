Practical Assignment · Git & GitHub

🛠️ Collaborative Feature Development

A real-world, scenario-based team assignment to master Git workflows in action.

Team Size: 2 Students
Mode: Collaborative (Pair)
Skills: Branching · PRs · Conflicts · Reviews
📋 The Scenario

You've just joined "DevBoard" – a startup building a task management web app.

Your team lead has set up a shared GitHub repository and assigned the two of you to develop two new features simultaneously, then merge them into the main codebase — just like real developers do every day. You'll use branches, pull requests, code reviews, and resolve a deliberate merge conflict along the way.

1 Team Roles

Decide who takes which role before you start. Both members participate in every phase, but ownership differs.

👤 Developer A — Repo Owner

Project Lead

  • Creates & owns the GitHub repository
  • Adds Developer B as a collaborator
  • Sets up the base project files
  • Builds the Add Task feature
  • Reviews Developer B's pull request
👤 Developer B — Collaborator

Feature Developer

  • Clones the shared repository
  • Builds the Delete Task feature
  • Opens a pull request for review
  • Reviews Developer A's pull request
  • Resolves the merge conflict

2 Phase 1 – Repository Setup

Step 1 Developer A

Create the Repository & Base Files

  • Create a public GitHub repository named devboard-app
  • Initialize it with a README.md
  • Clone it locally and create the following starter file:
# tasks.py — starter file Dev A creates tasks = [] def display_tasks(): if not tasks: print("No tasks yet.") for i, task in enumerate(tasks, 1): print(f" {i}. {task}")
  • Commit this file with message: "Initial commit: add tasks.py starter"
  • Push to main and add Developer B as a collaborator
Step 2 Developer B

Clone & Verify

  • Accept the collaboration invite
  • Clone the repository locally
  • Run git log --oneline to verify you can see Developer A's commit
  • Confirm you can view tasks.py locally

3 Phase 2 – Parallel Feature Development

Both developers now work simultaneously on their own branches. Do not wait for each other — this simulates real team parallelism.

Step 3 Developer A

Build the "Add Task" Feature

  • Create and switch to branch: feature/add-task
  • Add this function to tasks.py:
def add_task(task_name): tasks.append(task_name) print(f"✅ Task added: {task_name}")
  • Make at least 2 commits with meaningful messages
  • Push the branch to GitHub
Step 4 Developer B

Build the "Delete Task" Feature

  • Create and switch to branch: feature/delete-task
  • Add this function to tasks.py (edit the same file!):
def delete_task(task_index): if 0 <= task_index < len(tasks): removed = tasks.pop(task_index) print(f"🗑️ Removed: {removed}") else: print("Invalid task index.")
  • Also modify the display_tasks() function slightly (change the print format, e.g. add [TASK] prefix) — this will intentionally create a merge conflict later
  • Make at least 2 commits with meaningful messages
  • Push the branch to GitHub

4 Phase 3 – Pull Requests & Code Review

Step 5 Both Developers

Open Pull Requests

  • Each developer opens a Pull Request from their feature branch into main
  • Each PR must include a description explaining what the feature does and why
  • Each PR must include at least 1 screenshot or code snippet in the description
  • Assign the other team member as a Reviewer
Step 6 Both Developers

Review Each Other's Code

  • Leave at least 2 meaningful inline comments on the other person's PR (e.g., suggest an improvement, ask a clarifying question, note a potential edge case)
  • The PR author must respond to all comments — either make the suggested change or explain why not
  • Once satisfied, approve the PR using the GitHub "Approve" button
Step 7 Developer A

Merge the First PR

  • Merge Developer A's feature/add-task PR into main first (using Squash and Merge)
  • Delete the merged branch on GitHub

5 Phase 4 – Merge Conflict Resolution 🔥

Because both developers edited display_tasks(), merging the second PR will cause a conflict. This is intentional!

Step 8 Developer B

Pull Main and Encounter the Conflict

  • Locally, switch to your feature/delete-task branch
  • Run: git fetch origin then git merge origin/main
  • Git will report a merge conflict in tasks.py
  • Open the file, locate the conflict markers (<<<<<<<, =======, >>>>>>>), and study both versions
Step 9 Both Developers

Collaborate to Resolve the Conflict

  • Discuss (via GitHub comments or chat) which version of display_tasks() to keep, or write a new version that incorporates both changes
  • Developer B manually edits the file to remove conflict markers and produce the final version
  • Run git add tasks.py and git commit -m "resolve: merge conflict in display_tasks"
  • Push the resolved branch to GitHub
Step 10 Developer A

Merge the Second PR

  • Verify the conflict is resolved and the PR is green
  • Merge Developer B's feature/delete-task PR into main
  • Delete the merged branch

6 Phase 5 – Final Touches

Step 11 Both Developers

Update the README

  • Developer B creates a new branch: docs/update-readme
  • Update README.md to include: project description, how to run the app, and a list of features
  • Developer A reviews and merges this PR using a standard Merge Commit (not squash)
Step 12 Developer A

Tag the Release

  • On the final main branch, create an annotated tag:
git tag -a v1.0.0 -m "Release v1.0.0 - add and delete task features" git push origin v1.0.0
  • Create a GitHub Release from this tag with release notes

⚠️ Common Mistakes to Avoid
  • Never commit directly to main — always work on a branch
  • Don't merge your own PR without a review from your partner
  • Write meaningful commit messages — not "fix stuff" or "changes"
  • Always git pull before starting new work to avoid unnecessary conflicts
  • Do not delete conflict markers without actually resolving them
